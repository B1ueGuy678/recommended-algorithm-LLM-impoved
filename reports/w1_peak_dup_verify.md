## 1. 结论摘要

A3-C1 发现 big_matrix 有两个异常峰值日——**8/05（1,300,721 行）**与 **8/31（682,368 行）**，当时标注「未归因」。本报告检验的假设是：

> 这两个峰值是数据采集层面的重复写入，不是真实的行为爆发。

**在 big_matrix 内，该假设成立**，但两天的机制并不相同：

| | 8/05 | 8/31 |
|---|---|---|
| 原始行数 | 1,300,721 | 682,368 |
| 完全重复行（整行去重被去除） | 624,635（**48.02%**） | 341,184（**50.00%**） |
| 整行去重后 | 676,086 | 341,184 |
| 属于重复 (user,video) 对的行 | 1,252,231（**96.27%**） | 682,368（**100.00%**） |
| 机制 | 当日约 96% 的行被**写了两遍**，但其中只有一半是逐字段完全一致的副本 | **整日精确两两重复**（每个完全重复组的规模恰好 = 2） |
| 去重后 vs 相邻日均值 | +2.31% | +3.62% |

**8/31 是教科书式的批量双写**：`完全重复行 × 2 = 当日行数`，且当日每一行都属于某个重复对。数学上这等价于「每个整行重复组的规模恰好为 2」，不存在三重复制。

**8/05 不是纯粹的双写**：只有 48.02% 的行是逐字段完全一致的副本（若为严格双写应为 50.00%），但 96.27% 的行属于重复 (user,video) 对。两者相差的 18,916 行是「同一 (user,video)、字段值不同」的记录——即双写时部分字段（时间戳/播放时长等）落在了不同的值上。

**关键副产品（对 B2 有直接价值）**：全局 965,819 条完全重复行 **100% 来自这两天**（8/05 的 624,635 + 8/31 的 341,184 = 965,819），其余 26 天完全重复行全部为 **0**。见 §5。

### 2.1 上游 A4 报告的一处口径错误（本报告更正）

`reports/w1_data_anomaly.md` §2 的表格把 **14.6961%** 标为重复对「占总行数」的比例。该数字实际是 `重复 pair 数 ÷ 总行数` = 1,841,544 / 12,530,806，即**用 pair 数除以行数**——两个量纲不同的数相除，没有解释意义。

正确口径是：

| 说法 | 值 | 含义 |
|---|---|---|
| 重复 pair 数 / 总行数 = 14.6961% | — | **量纲错误，不应使用** |
| 重复 pair 涉及**行数** / 总行数 = **32.4910%** | 4,071,381 / 12,530,806 | 这是「多少行卷入了重复」的正确答案 |

`scripts/w1_data_anomaly.py` 第 74 行的 `pct_dup_pairs = dup_pairs / total` 是错误来源（分母应为 `dup_pair_rows`）。**本轮不修改 A4 脚本与报告**——它是已提交的产物，改它会让 A4 报告的历史数字失去可追溯性；本报告作为更正记录，建议在 A4 下次修订时一并处理。

### 3.1 一个反直觉之处：峰值日的「平均重复次数」反而更低

| 日期 | 重复 pair 数 | 涉及行数 | 平均每对重复次数 |
|---|---|---|---|
| 8/04（对照） | 13,179 | 32,177 | **2.442** |
| 8/06（对照） | 12,906 | 33,874 | **2.625** |
| 8/05（峰值） | **608,680** | 1,252,231 | **2.057** |
| 8/31（峰值） | 329,868 | 682,368 | **2.069** |

正常日的重复是**少数 pair 被反复观看多次**（平均 2.4–2.6 次，全局最大 2,224 次）——这是真实的用户反复播放行为。而峰值日的重复是**大量 pair 各被记录两次**（平均 2.06 次）。**两者形状不同**，这正是「峰值 ≠ 行为爆发」的量化证据：行为爆发会抬高每对的重复次数，批量双写只会抬高重复 pair 的数量。

## 4. 三级去重的影响面

去重强度从弱到强，删除量如下：

| 去重口径 | 相对原始删除行数 | 占全量 | 其中来自正常日（26 天） |
|---|---|---|---|
| **整行完全一致去重**（`df.unique()`） | **965,819** | 7.71% | **0** |
| **日内 (user,video) 去重**（键 = `user_id,video_id,date`） | 1,327,875 | 10.60% | **331,824（24.99%）** |
| **全局 (user,video) 去重** | 2,229,837 | 17.79% | **≥ 331,824**（跨日阶段那 901,962 行横跨多个日期，删除必然涉及至少两天，**不可归属到单日**） |

三级去重阶梯（数字由脚本内断言保证自洽）：

```
原始                                  12,530,806
  − 整行完全重复                         965,819   ← 100% 来自 8/05 与 8/31
  = 整行去重后                        11,564,987
  − 日内同 pair 不同值                    362,056   ← 正常日 331,824 + 峰值日 30,232
  = 日内 (user,video) 去重后          11,202,931
  − 跨日重复 pair                         901,962   ← 横跨不同日期，不可归属单日
  = 全局 (user,video) 去重后          10,300,969
```

**这是本报告对 B2 最有价值的输出**：

- **整行去重是「只修坏天」的手术刀**——它删除的 965,819 行全部落在 8/05 与 8/31，对其余 26 天的影响**恰好为 0**（V12 PASS）。用它修数据不会损失任何正常日的信号。
- **pair 级去重不是**——无论日内还是全局口径，它都会从正常日删除大量行（日内口径 331,824 行，全局口径再加 901,962 行跨日重复）。这些被删掉的不是脏数据，是**真实的反复观看行为与跨天留存行为**。

因此「如何处理重复记录」在数据层面分裂成两个**性质不同**的问题：

1. **数据清洗问题**：8/05 与 8/31 的批量双写要不要修？——整行去重即可，零副作用。
2. **建模选择问题**：正常日的反复观看（同日多次 + 跨日多次）要不要压缩成一条？——这是行为序列建模的决定，与数据质量无关。

## 5. 对 B1 的实际影响

**B1 的切分窗口不需要修改。** 三条理由，全部有数字支撑：

1. **训练期峰值 8/05 经整行去重后回落到 676,086 行**，与相邻日均值 660,834 的偏差 **+2.31%**（V5 PASS），属正常波动。
2. **测试期峰值 8/31 经整行去重后回落到 341,184 行**，与相邻日均值 329,277 的偏差 **+3.62%**（V8 PASS）。**测试期不存在真实的行为异常。**
3. **去重前 全期 max/median = 3.557，去重后 = 1.926**（V10 PASS）。极端的单日离群消失，剩下的 1.93 倍是中段（8/01–8/10）相对首尾段的**固有量级差**，不是异常。

### 5.1 训练期不连续（7/12 → 8/01 断 19 天）：W3 的显式红线

这是数据集本身的结构限制，B1 已接受，**不是错误**。但它对 W3/W4 的序列模型是硬约束：

> **W3/W4 构造行为序列时，必须在 7/12 → 8/01 的段间显式截断，不得把这段空白当作行为序列的自然延续。**

同理，8/10 → 8/27 的 16 天空窗也一样。若用 DIN/DIEN 等序列模型却让序列跨越空窗，模型会学到「相邻两次交互间隔 19 天」这种在数据里从不存在的模式。**建议在样本构造阶段用 `date` 的段边界（而非行序）切序列。** 该决定记录于此，供 W3 执行时对照。

## 6. 判据缺陷（自曝）：V4 是设计不当的判据

**V4「按完全重复行去重后，8/05 不再是全期峰值日」判定 FAIL。**

去重后逐日 argmax 仍然是 8/05（676,086 行），第二名是 8/06（674,263 行）——**差距仅 1,823 行，0.27%**。

这是**判据设计不当**，不是数据结论：

- V4 用「argmax 是否易主」做判据。在 8/01–8/10 这一段内每日行数都挤在 57 万–68 万之间，argmax 是一个**刀刃上的身份判断**，0.27% 的差距就能翻转结论。
- V4 想测的其实是「峰值是否消失」。正确的量化判据是 V5（去重后与相邻日均值的偏差 ≤ 20%），它 **PASS**（+2.31%）；以及 V10（去重后无单日超过中位数 2 倍），它 **PASS**（3.557 → 1.926）。
- **结论不依赖 V4。** 无论 V4 判定如何，「8/05 的原始峰值是批量双写造成的、去重后与相邻日持平」这一结论都由 V1/V2/V5/V12 共同支撑。

**我不修改 V4 的表述让它变绿。** 保留 FAIL，用它记录「用 argmax 身份做判据」这个错误模式——本项目的验收脚本此前已出现过四次类似问题（见 `reports/w1_acceptance_A1A2.md`），这是第五次。

同类的临界余量问题还有一处：**V10 的阈值 2.0 与实测值 1.926 只差 3.8% 余量**。它虽然 PASS，但同样接近临界，不应被当作「有充分安全边距」的证据；真正有意义的是 3.557 → 1.926 这个下降本身。
